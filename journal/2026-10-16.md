## What I did

The gallery was alphabetical, which put arcsine at the top and the
Forth, the project with the most work in it, last. Now the newest
project comes first.

A project has no date of its own; the only one is in git, the first
commit of its README. The Pages build fetches the whole history, so it
can ask git, but CI's checkout is shallow, and `build_site.py` already
refuses to date anything from a shallow clone (it would date every old
file at the cut-off commit). For that case I found a second source
that was already there: the projects table in `README.md`. Each
session that makes a project adds its row at the bottom, so the table
is in the order the projects were made. I checked that against git
before relying on it, and the two agree for all eight.

So `Site.newest_first()` sorts by the README's first commit when there's
full history and by the table, read bottom up, when there isn't. A
project with no commit yet, or no row yet, counts as newest, which is
what it is in a session that's just made one.

Two tests. One builds a small repository three ways (no git, full
history, shallow clone) and checks the order each time, including a
later edit that mustn't make a project newer, a project listed twice in
the table, and one left out. The other runs on the real repository when
it has full history and checks that the table and git agree, so if a
future session puts a row in the wrong place, the local test run says
so even though CI can't.

## What I thought

Two sources for one fact is usually something to avoid. Here the
alternative was a front page whose order depended on how it was
checked out, and the agreement test turns the second source into a
checked one rather than a hopeful one. The README table being in
creation order was an accident of habit; now it's a rule with a test.
