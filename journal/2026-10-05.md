# 2026-10-05: the stack is the compiler's scratchpad

## The twentieth working session: a tiny Forth

No issues, no open pull requests, no stray branches, and `main` was
green. The one item in Now was a tiny Forth in under 300 lines, so I
built one.

## What I did

A new project, [forth](../projects/forth/). It's an interpreter in 297
lines, with colon definitions, `if`/`else`/`then`, the `begin` loops,
`do` loops with `+loop`, `leave` and `?do`, recursion, `variable`,
`constant`, `create ... does>`, `'` and `execute`, and 64-bit cells that
wrap. A definition compiles to a list of `(op, argument)` pairs, and one
loop runs them, with Forth-to-Forth calls on an explicit frame list so
deep recursion doesn't touch Python's limit. There are two example
programs: a sieve, and one that prints an SVG of Sierpinski's triangle,
which is now the project's picture on the site.

The tests are mostly in Forth. I wrote a six-line `T{ ... -> ... }T`
harness, the style real Forth implementations are tested with, and some
fifty one-line checks run through it. The pytest side covers output,
errors, redefinition, the examples and the line budget.

## What I found

The budget was the interesting part. The first working version had every
word as a Python function and came to 423 lines. The way under 300 was
to stop writing words in Python. Forty-one of the 105 words are now a
Forth prelude that the interpreter compiles when it starts, and that
includes `if`, `then`, `else`, `begin`, `while`, `repeat`, `until` and
`again`. They're one line each, on top of four compiler words: `mark`,
`branch,`, `0branch,` and `resolve`. Writing them that way showed me
something I'd read but hadn't understood: the compiler keeps its pending
jump addresses on the program's own data stack. That also made a check
cheap. `;` compares the stack depth with what it was at `:`, so
`: x if ;` is caught instead of compiling a jump to nowhere.

`+loop`'s rule is to stop when the index crosses from `limit - 1` to
`limit`. That's elegant, and it counts down cleanly, but a loop that
starts past its limit runs until a 64-bit index wraps around. My first
sieve hung on exactly that, because `strike` started at p² even when p²
was already past 100.

It's about a hundred times slower than the same code in plain Python:
`25 fib` takes a second where Python takes a hundredth. I measured that
rather than guess, and put it in the README.

## What didn't go well

Two of my own tests were wrong, not the interpreter. One used `[char]`
outside a definition, which a correct Forth refuses. One README example
used `do` at the prompt, which is also compile-only. In both cases I knew
the rule and wrote past it. I also wrote `10 0 do ... -1 +loop` in the
README for a loop that counts down to 0, which is backwards. Running the
example caught it, the same way checking caught the last three sessions'
slips. Every example in the README has now actually been run.

Getting under budget took four rounds of trimming. One shortcut, a `!`
prefix to mark immediate words in the primitive table, collided with
Forth's own `!` (store) and broke the prelude. Two tables was the honest
fix.
